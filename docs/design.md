# 个人创作助手系统 设计文档

## 1. 系统目标

打造一个以作者风格蒸馏为核心的多Agent创作系统，实现：
- 精确蒸馏小说作者的写作手法、故事构思、文笔特征，形成严格的写作规则
- 基于蒸馏规则创作小说，规则优先级 > 大模型自带写作能力
- 支持以时事热点为素材进行小说创作，小说时间独立运行，按主题匹配热点
- 长篇小说创作不崩人设、不丢伏笔、前后逻辑自洽，无明显AI味
- 多Agent协作，各角色职责单一，共享统一状态层
- 为后续自媒体文章、抖音漫画、电商运营模块预留扩展接口

---

## 2. 架构总览

```
用户 ←→ 总编助理Agent ←→ Python编排内核 ←┬→ 蒸馏Agent集群
                                          ├→ 创作Agent集群
                                          ├→ 工具层（爬虫/生图/文件IO）
                                          └→ 共享状态层（小说圣经）
```

### 核心设计原则
1. **状态先行**：所有Agent不持有私有记忆，所有决策基于共享状态层，所有更新写回共享状态层
2. **规则硬约束**：蒸馏出的写作规则分层级，高优先级规则不可违反
3. **宁可不更，不写崩**：合理性 > 完成任务，无法自然融入的热点绝不硬塞，写不下去允许停更
4. **控制面与创作面分离**：用户只与总编助理对话，所有指令经过理解、诊断、确认后才落地到状态层，创作Agent只对状态层负责
5. **轻伏笔/重伏笔分级**：预判类素材只埋轻伏笔（闲笔细节），主线级重伏笔必须等事件明确后再埋

## 3. 核心概念与数据结构

### 3.1 作者风格规则（六层结构，优先级从高到低）

所有规则为Markdown文件，内容是可执行的写作指令，不是形容词描述。

| 文件 | 层级 | 内容要求 |
|------|------|----------|
| `layer0_redlines.md` | 绝对红线 | 作者绝对不会写的题材、情节、价值观；明确的禁止项；核心写作戒律。每条规则是"必须/绝对不"开头的明确陈述。 |
| `layer1_meta.md` | 写作元规则 | 叙事视角、章节字数范围、爽点密度（每多少字一个爽点）、叙事节奏偏好、视角切换规则、信息揭示节奏。 |
| `layer2_prose_dna.md` | 文笔DNA | 句式长短分布（量化：短句<10字占比、中句、长句占比）；常用词清单（至少50个）；禁用词/AI高频词清单（至少30个，包含"不仅喃喃道""眼中闪过一丝"等）；对话风格（口语化程度、口头禅、脏话比例、不同人物对话区分度）；描写偏好（环境/心理/动作描写比例，各占多少百分比）；修辞手法偏好。 |
| `layer3_characters.md` | 人物塑造规则 | 主角人设模板（出身、性格、金手指类型、成长弧线规律）；配角功能类型与出场规律；反派塑造方式；人物对话区分原则；绝对不能OOC的行为红线。 |
| `layer4_structure.md` | 故事结构规则 | 开篇钩子类型（前多少字必须出什么冲突）；转折触发规律；高潮设计特点；伏笔埋设与回收节奏（通常埋多久回收）；章节结尾留钩子的方式；大高潮前的铺垫规律。 |
| `layer5_antipatterns.md` | 反模式库 | 该作者绝对不会用的烂俗桥段；AI写作常见毛病（针对该作者风格的具体表现）；要刻意避免的写法；废稿中积累的错误模式。 |

另外有`corrections.json`存储用户的所有纠正记录，优先级高于所有层：
```json
[
  {
    "id": "uuid",
    "timestamp": "ISO时间",
    "scene": "具体场景描述",
    "wrong": "错误写法/行为",
    "correct": "正确写法/行为",
    "applied_scope": "全局/某人物/某类情节"
  }
]
```

### 3.2 小说圣经（Novel Bible）目录结构

每本小说一个独立目录：
```
workspace/novels/{novel_slug}/
├── author_style/              # 3.1定义的风格规则
├── worldbuilding/
│   ├── setting.md             # 时代背景、核心设定、地理/社会环境
│   ├── power_system.md        # 力量体系（如需要，含明确的等级、边界、禁忌）
│   └── locations.md           # 重要地点，含环境描写参考
├── characters/                # 每个人物一个md文件
│   └── {character_slug}.md
├── plot/
│   ├── outline.md             # 总大纲+分卷大纲
│   ├── timeline.md            # 小说内时间线（事件-章节对应表）
│   ├── foreshadow_map.json    # 伏笔表
│   └── chapter_outlines/      # 每章细纲，一个文件一章
├── material_library/
│   ├── hotspots/              # 热点素材，一个文件一个事件
│   ├── seed_materials.md      # 轻伏笔池/预判素材
│   └── user_ideas.md          # 用户提供的想法，总编助理录入
├── chapters/                  # 已写章节，chapter_XXX.md，序号3位补零
├── drafts/                    # 废稿库，含废弃原因记录
├── editor_ideas/              # 总编想法库
│   ├── pending.md             # 待决策想法
│   ├── applied.md             # 已落地想法
│   └── rejected.md            # 已放弃想法+原因
└── meta.json                  # 小说元数据
```

## 4. Agent角色详细设计

所有Agent的输入输出都是结构化的，不直接写自然语言指令。每个Agent有独立的System Prompt，存储在`prompts/`目录下。

### 4.1 总编助理Agent（用户唯一接口）

**职责**：
- 接收用户所有输入（自然语言，不用结构化）
- 意图分类：反馈/新想法/配置修改/版本操作/闲聊探讨
- 问题诊断：用户反馈"写得不好"时，联合审稿Agent定位根因（哪一层规则/哪个人物/哪个情节出问题）
- 给出处理方案：重大改动先给选项让用户确认，小问题可直接修复
- 管理总编想法库：记录待决策想法，写到对应章节时主动提醒
- 执行确认后的操作：更新状态层、触发回滚、启动重新生成等

**绝对不做**：
- 不直接写小说内容
- 不跳过用户确认直接修改核心规则（Layer 0/大纲/人物设定）
- 不把用户的情绪化评价直接传给创作Agent

### 4.2 风格蒸馏Agent集群

#### 4.2.1 文本预处理Agent
- 输入：原始小说文件（txt/epub）
- 输出：清洗后的纯文本，按章节拆分，去除广告、作者说、无关内容
- 职责：格式解析、文本清洗、章节划分、元数据提取（章节数、总字数）

#### 4.2.2 量化统计Agent
- 输入：清洗后的文本
- 输出：量化统计数据（句式长度分布、词汇频率、对话占比、描写占比、各类型场景出现频率、爽点间隔统计）
- 职责：做所有可量化的统计，为Layer 2和Layer 1提供数据支撑

#### 4.2.3 文学分析Agent
- 输入：清洗后的文本 + 量化统计结果
- 输出：Layer 0/1/3/4的规则草稿
- 职责：定性分析叙事视角、人物塑造方式、故事结构、开篇手法、转折规律等

#### 4.2.4 反模式检测Agent
- 输入：清洗后的文本
- 输出：Layer 5反模式库草稿 + 该作者不会用的桥段清单 + AI高频词在该作者作品中的出现情况统计
- 职责：专门找"什么是这个作者绝对不会写的"，识别AI常用写法和该作者风格的差异

#### 4.2.5 蒸馏校验Agent
- 输入：六层规则草稿、清洗后的原作文本
- 过程：
  1. 调用写作Agent（不更新圣经状态），用当前规则写3段各1000字的试写稿，分别覆盖：对话场景、动作场景、抒情/心理场景
  2. 从原作中随机抽取3段对应类型、长度相近的文本，打乱顺序编号
  3. 本Agent逐段判断：这段是"原作"还是"AI生成"，并写出判断依据
  4. 如果判断准确率>60%（能轻易分辨），则根据判断依据指出AI稿的问题点，对应修正相关层的规则
  5. 迭代2-3轮，直到判断准确率接近50%（随机猜测水平）
- 输出：最终的六层规则文件，校验报告（包含每轮迭代的问题和修正点）

### 4.3 创作Agent集群

#### 4.3.1 热点采集Agent
- 输入：时间范围（开书阶段是过去12个月，日更阶段是当天）
- 输出：标准化的热点素材文件（存入material_library/hotspots/）
- 第一阶段MVP：支持手动导入文本，自动解析成标准格式；预留爬虫接口
- 职责：热点去重、分类、核心冲突提炼、可小说化点分析

#### 4.3.2 素材匹配Agent
- 输入：当日热点列表 + 小说当前进度（当前章节大纲、人物位置、伏笔表状态）
- 输出：四类素材清单：
  - A类：当前可用（自然融入本章）
  - B类：适合埋轻伏笔（本章加闲笔）
  - C类：入库备用
  - D类：待观察（事件刚露头，标记预判方向）
- 职责：判断每个热点和当前剧情的契合度，拒绝硬塞

#### 4.3.3 开书策划Agent
- 输入：作者风格规则 + 过去12个月热点分析报告 + 用户初始想法（如有）
- 输出：开书策划案，包含：
  - 时代背景与核心矛盾群（从全年热点提炼）
  - 核心切入点（故事从哪里开始）
  - 主角设定（符合作者擅长的类型，且能自然接触各类矛盾）
  - 分卷大纲（每卷主题、能承载的热点类型）
  - 初始世界观、主要人物设定
- 职责：不是想一个点子，而是搭一个能写100万字以上、能承载未来各类热点的稳定框架

#### 4.3.4 大纲Agent
- 输入：总大纲当前进度 + A/B类素材 + 伏笔表 + 相关人物卡
- 输出：本章细纲（chapter_outlines/chapter_XXX.md）
- 细纲必须包含：
  - 本章核心事件
  - 出场人物列表
  - 情绪节奏曲线（铺垫-冲突-转折-高潮-收尾）
  - 要收的伏笔、要新埋的伏笔
  - 要融入的热点素材及融入方式
  - 本章结尾钩子
- **强制校验步骤（三问）**：
  1. 本章人物行为符合其性格吗？有OOC风险吗？
  2. 热点融入自然吗？读者会觉得突兀吗？
  3. 这一章放在整本小说里，节奏对吗？会不会影响后续剧情？
- 三问任一不通过，必须调整细纲；调整后仍不通过，放弃当前热点，按原计划推进；如果原计划推进也不合理，出具"停更建议"说明原因。

#### 4.3.5 写作Agent
- 输入：
  - 六层风格规则（全量加载，但Layer 0-2重点）
  - 本章细纲
  - 相关人物卡（只加载本章出场的）
  - 上一章结尾（最后1000字）
  - 本章要用到的热点素材
  - 要埋/收的伏笔列表
- 输出：
  1. 本章完整正文（Markdown格式）
  2. **本章变更摘要**（结构化，供状态更新Agent使用）：
     - 出场人物列表
     - 每个人物的状态变化（心理变化、关系变化、获得/失去什么）
     - 新埋伏笔列表（内容、位置、预计回收方向）
     - 回收伏笔列表
     - 小说内时间推进了多久
     - 用了哪些热点素材、如何融入的
- 写作规则：
  - 严格按Layer 0-Layer 5顺序遵守规则，高优先级规则冲突时低优先级让道
  - 禁止使用Layer 2禁用词清单里的词
  - 写完先自检：有没有违反规则？有没有AI味的句子？有没有不符合人物的对话？
  - 允许中途阻塞：写不下去时输出"写作阻塞报告"说明卡在哪里、为什么写不下去，打回大纲Agent，不要硬凑
- 上下文策略（第一版实现方式）：
  - 编排器在调用写作Agent前，根据大纲中列出的出场人物，加载全部相关人物卡
  - 加载上一章最后1000字衔接
  - 加载伏笔表中状态为planted、计划近期回收的条目
  - 不加载整本小说内容；如果需要回忆更早的情节，写作Agent在变更摘要中提出需要哪部分信息，编排器检索后补充
  - Layer 0-2全量加载，Layer 3-5只加载和本章相关的片段

#### 4.3.6 审稿Agent集群（三个独立审稿，第一版顺序调用，后续可优化并行）

**风格审稿人**：
- 对照六层规则逐段检查
- 重点：文笔像不像？有没有AI味？对话符合人物吗？节奏对吗？有没有用禁用词？
- 输出：风格问题清单，标位置、问题类型、修改建议

**逻辑审稿人**：
- 对照圣经（人物卡、时间线、伏笔表、前面章节）检查
- 重点：人物OOC吗？前后矛盾吗？伏笔对得上吗？时间线乱了吗？力量体系崩了吗？
- 额外职责：每写完10章，触发一次全本一致性检查，扫描所有伏笔回收状态、人物事件一致性、时间线连续性
- 输出：逻辑问题清单，标位置、问题严重程度（致命/一般/建议）、修改建议

**合理性审稿人**：
- 站在读者视角检查
- 重点：热点融入硬不硬？剧情推进合理吗？有没有为了爽/蹭热点强行降智？读者会出戏吗？有没有"说教感"？
- 输出：合理性问题清单，标位置、读者可能的吐槽点、修改建议

#### 4.3.7 审稿汇总Agent
- 输入：三个审稿人的问题清单
- 输出：审稿结论：
  - 通过：无致命问题，一般问题<3个 → 进入状态更新
  - 修改后通过：有一般问题，无致命问题 → 打回写作Agent按意见修改
  - 重写：有致命逻辑/风格问题 → 打回大纲Agent重新出细纲
  - 废稿：怎么改都不合理 → 存入废稿库，记录原因，触发停更建议
- 规则：三个审稿人有一个给出"致命问题"，就必须重写，不能绕过

#### 4.3.8 状态更新Agent
- 输入：最终定稿的本章正文
- 职责：**写完一章必须更新圣经，这是硬性要求，不能跳过**
  - 更新每个出场人物的"已发生关键事件"，记录心理变化、关系变化
  - 推进timeline.md，更新小说内当前时间
  - 更新foreshadow_map.json：新埋的加入，回收的改状态
  - 更新素材库：用了的素材标记used，埋了轻伏笔的标记planted_seed
  - 更新outline.md，标记本章完成，更新下一章预计方向
  - 更新meta.json的current_chapter和时间戳
  - 所有文件变更提交版本控制

## 5. 工作流设计

### 5.1 作者风格蒸馏流程
```
1. 用户提供小说文件（txt/epub）
2. 文本预处理 → 清洗拆分
3. 量化统计Agent + 文学分析Agent + 反模式检测Agent并行工作
4. 生成六层规则草稿
5. 蒸馏校验Agent迭代校验2-3轮（试写→分辨→修正）
6. 输出最终规则文件
7. 总编助理给用户看规则摘要，说明哪些是硬红线，用户可调整
8. 规则确认后存入novel_slug/author_style/
```

### 5.2 开书流程
#### MVP阶段（手动开书）：
```
1. 用户确认蒸馏完成，手动提供：小说名、初始世界观设定、主要人物卡、分卷大纲
2. （可选）用户手动导入一批热点素材，系统自动解析成标准格式存入素材库
3. 总编助理确认所有初始设定无误
4. 系统初始化小说圣经目录结构，写入用户提供的设定、人物、大纲
5. （可选）用户手动指定前几章细纲，或让大纲Agent基于总大纲生成前三章细纲
6. 走日更流程写前三章（试写期）
7. 三章写完，总编助理汇总给用户，用户确认没问题则正式开书，有问题调整后重写
```

#### 第二阶段（自动开书策划，MVP后实现）：
```
1. 用户确认蒸馏完成，提供初始想法（可选）
2. 热点采集Agent回溯采集过去12个月热点
3. 热点分析：分类、提炼核心矛盾群、预判热点趋势
4. 开书策划Agent生成开书策划案
5. 总编助理把策划案给用户确认，用户可修改调整
6. 确认后初始化小说圣经目录结构，创建初始人物卡、世界观、分卷大纲
7. 筛选过去热点，适合前期剧情的直接融入前几章大纲
8. 预判的未来方向填入seed_materials.md
9. 生成前三章细纲
10. 走日更流程写前三章（试写期）
11. 三章写完，总编助理汇总给用户，用户确认没问题则正式开书，有问题调整后重写
```

### 5.3 日更连载流程
```
1. 触发日更（用户手动触发，或定时自动触发）
2. 热点采集Agent采集当日热点
3. 素材匹配Agent分类匹配，输出A/B/C/D四类素材
4. 大纲Agent生成本章细纲，过三问校验
   - 校验不通过→调整→仍不通过→放弃热点→按原计划
   - 原计划也不通→出具停更建议交总编助理
5. 写作Agent写正文，自检
   - 写作阻塞→打回大纲重想
6. 三个审稿Agent并行审稿
7. 审稿汇总Agent给出结论
   - 通过→进入下一步
   - 修改后通过→返回修改
   - 重写→返回大纲
   - 废稿→存废稿库→停更建议
8. 状态更新Agent更新圣经所有相关文件
9. 版本提交
10. 总编助理检查editor_ideas/pending.md，提醒用户相关待决策想法
11. 输出本章给用户
```

### 5.4 纠正/迭代流程
```
1. 用户对总编助理说某章/某个人物/某种写法不对
2. 总编助理意图分类，联合审稿Agent诊断根因：
   - 是某层规则缺失？
   - 是人物卡设定不对？
   - 是大纲节奏问题？
   - 是具体文字问题？
3. 给出处理方案和选项，用户确认
4. 执行更新：
   - 规则问题→更新对应layer文件+corrections.json
   - 人物问题→更新对应人物卡
   - 章节问题→打回重写受影响章节
   - 大纲问题→调整大纲
5. 纠正记录存入corrections.json或editor_ideas/，未来不犯同样错误
```

### 5.5 回滚流程
```
1. 用户要求回滚到第N章
2. 总编助理确认回滚范围：
   - 只回滚正文？还是连带大纲、人物状态、伏笔一起回滚？
3. 用户确认后：
   - chapters/中保留N章之后的章节但移入drafts/rollback_XXX/
   - 从版本控制恢复第N章结束时的圣经状态（人物卡、时间线、伏笔表、大纲）
   - 记录回滚操作原因
   - meta.json更新current_chapter为N
```

## 6. 去AI味与防写崩机制

### 6.1 写作阶段硬约束
1. **禁用词强制检查**：写完后自动扫描Layer 2禁用词，出现必改
2. **句式分布强制对齐**：统计本章句式长度分布，和作者量化数据偏差超过阈值的段落必须重写
3. **对话区分度检查**：随机抽两段对话，隐去人名，让审稿Agent猜是谁说的，猜不出来说明对话没区分度，要改
4. **"不要说，要展示"检查**：直接陈述情绪的句子（"他很生气""她非常难过"）超过阈值必须改成动作/神态/细节描写

### 6.2 反任务导向机制
1. **三问校验**：大纲必须过合理性三问才能进入写作
2. **写作阻塞权**：写作Agent可以中途停写，说明原因，不用硬凑
3. **停更建议权**：当所有Agent都认为今天硬写会崩，可以建议停更，由总编助理请示用户
4. **独立审稿**：写作Agent不能自己审自己，三个审稿人独立给出意见
5. **废稿归档**：废稿不删除，记录原因，形成反模式库，避免重复踩坑

### 6.3 长篇一致性保障
1. **按需加载上下文**：每次写作不依赖大模型记忆，精确检索需要的人物卡、伏笔、设定
2. **人物卡事件记录**：每个人物经历的事实时更新，写他之前必须看他最近经历了什么
3. **伏笔表追踪**：所有伏笔都有记录，定期（每10章）检查伏笔回收情况，不遗忘
4. **时间线同步**：小说内时间精确到天，避免"上周还穿短袖这周就过年"的矛盾
5. **版本控制**：每章写完自动提交，可回滚到任意时间点

### 6.4 热点融入约束
1. **轻/重分级**：只有轻伏笔可以基于预判埋，主线伏笔必须等事件落地
2. **适配优先于蹭**：热点必须适配人物和剧情，而不是改剧情适配热点
3. **合规过滤**：政治敏感、重大灾难、未定论司法事件直接过滤不入素材库
4. **匿名化处理**：所有热点人物改名字、改身份，只取事件骨架和冲突模式，不映射真人

## 8. 技术选型

- **语言**：Python 3.10+
- **LLM调用**：支持OpenAI/Anthropic/国内大模型API，封装统一LLM客户端，支持配置切换
- **Prompt管理**：所有Agent的System Prompt用独立Markdown文件存储，加载后填充变量
- **文件格式**：所有状态文件用Markdown（人可读、可手动编辑）+ JSON（结构化数据）
- **版本控制**：系统级gitPython，每章/每次规则变更自动commit
- **文本解析**：
  - txt：直接读取，编码自动检测（chardet）
  - epub：预留ebooklib接口
- **依赖管理**：requirements.txt + pyproject.toml
- **CLI入口**：argparse，未来可用click升级

   - 检查AI味、人物一致性、逻辑问题

## 11. 已知风险与应对

| 风险 | 应对措施 |
|------|----------|
| LLM上下文窗口不够，加载不了所有规则 | 规则分层加载，Layer 0-2全加载，Layer 3-5按需要检索相关片段；人物卡只加载本章出场的 |
| 蒸馏出来的规则不像，试写AI味重 | 多轮校验迭代，反模式检测Agent专门找AI和作者的差异，correction层持续积累纠正 |
| 长篇写下去前后矛盾 | 写作Agent必须输出本章变更摘要，状态更新Agent基于摘要更新圣经；每10章逻辑审稿人做全本一致性检查；所有状态变更可追溯 |
| 硬塞热点导致剧情崩 | 大纲三问校验，合理性审稿人一票否决权，宁可不更不硬塞 |
| Agent之间互相踢皮球死循环 | 编排内核设置最大重试次数（重写最多3次），超过则转人工（总编助理请示用户） |
| Prompt太长效果下降 | 每个Agent职责单一，Prompt只写自己的职责和输出要求，不冗余；通用规则拆分到单独文件按需include |
| 状态更新不及时或更新错误 | 状态更新完全基于写作Agent输出的结构化变更摘要，不凭空猜测；每次更新后git commit，出错可回滚 |
| 用户不知道怎么和系统交互 | CLI提供chat模式，用户用自然语言说话即可，总编助理负责理解意图；所有重大操作都有确认步骤 |
| 没有LLM API Key无法运行 | 首次运行config init引导用户配置，提供清晰的配置说明 |
